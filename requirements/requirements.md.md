# Project Requirements: Smart Meeting & Appointment Management System

## 1. Project Overview

พัฒนาระบบสำหรับจัดการการนัดหมาย การประชุม และการประชุมที่เกี่ยวข้องกับโครงการ (Project-based Meetings) โดยเน้นการจัดเก็บและบริหารข้อมูลด้วยฐานข้อมูลเป็นหลัก

ระบบควรช่วยลดขั้นตอนในการสร้างนัดหมาย เลือกผู้เข้าร่วม ส่งคำเชิญ แจ้งเตือน และติดตามบริบทจากการประชุมครั้งก่อน โดยรองรับการใช้ลิงก์ประชุมออนไลน์ เช่น Microsoft Teams ที่ผู้ใช้สร้างไว้แล้ว

การส่งอีเมล ไฟล์ `.ics` และ AI เป็นฟังก์ชันสนับสนุนระบบ ไม่ใช่แกนหลักของโครงงาน นักศึกษาจะต้องวิเคราะห์และออกแบบโครงสร้างฐานข้อมูลที่เหมาะสมจาก Requirements และ Business Rules ที่กำหนด โดยโจทย์นี้ไม่ได้กำหนด ER Diagram หรือ Database Schema ให้ล่วงหน้า

---

## 2. Project Objectives

ระบบควรสามารถ:

1. จัดการข้อมูลสมาชิกและข้อมูลติดต่อ
2. จัดสมาชิกเป็นกลุ่มเพื่อเลือกผู้เข้าร่วมได้รวดเร็ว
3. สร้างและจัดการนัดหมาย/การประชุม
4. เชื่อมโยงผู้เข้าร่วมหลายคนกับการประชุม
5. รองรับลิงก์ประชุมออนไลน์ที่สามารถนำกลับมาใช้ซ้ำได้
6. ส่งคำเชิญผ่านอีเมลและไฟล์ `.ics`
7. จัดการการแจ้งเตือนก่อนถึงเวลาประชุม
8. รองรับทั้งการประชุมแบบครั้งเดียวและการประชุมที่ต่อเนื่องภายใต้โครงการ
9. จัดเก็บ Meeting Notes เอกสาร ลิงก์ และข้อมูลประกอบการประชุม
10. ติดตามประเด็นค้าง การตัดสินใจ และงานที่เกิดจากการประชุม
11. ใช้ AI เพื่อช่วยเตรียมข้อมูลก่อนการประชุมที่มีบริบทต่อเนื่อง

---

# 3. Functional Requirements

## FR-01 User and Contact Management

ระบบต้องสามารถจัดเก็บข้อมูลบุคคลที่อาจถูกเชิญเข้าร่วมการประชุมได้

ข้อมูลที่เหมาะสมควรครอบคลุมอย่างน้อย:

- ชื่อ
- อีเมล
- ข้อมูลสำหรับระบุตัวบุคคล
- สถานะการใช้งาน
- ข้อมูลประกอบอื่นที่จำเป็นต่อการติดต่อ

ระบบควรรองรับทั้งบุคคลที่เป็นผู้ใช้งานระบบ และบุคคลภายนอกที่ไม่ได้มีบัญชีในระบบแต่สามารถถูกเชิญเข้าร่วมประชุมได้

---

## FR-02 Contact Group Management

ผู้ใช้ต้องสามารถสร้างกลุ่มของบุคคลสำหรับใช้งานซ้ำได้ เช่น:

- ทีมโครงการ
- คณะกรรมการ
- กลุ่มอาจารย์
- กลุ่มนักศึกษา
- ทีมวิจัย
- กลุ่มผู้บริหาร

ผู้ใช้ต้องสามารถ:

- สร้างกลุ่ม
- แก้ไขข้อมูลกลุ่ม
- เพิ่มสมาชิกเข้ากลุ่ม
- นำสมาชิกออกจากกลุ่ม
- ดูสมาชิกทั้งหมดของกลุ่ม

บุคคลหนึ่งสามารถอยู่ได้มากกว่าหนึ่งกลุ่ม

---

## FR-03 Quick Invite

เมื่อสร้างการประชุม ผู้ใช้ควรสามารถเลือกผู้เข้าร่วมได้อย่างรวดเร็วโดย:

- เลือกบุคคลทีละคน
- เลือกจากกลุ่มที่มีอยู่
- เพิ่มอีเมลของบุคคลภายนอกตามความเหมาะสม

เมื่อเลือกกลุ่ม ระบบต้องสามารถนำสมาชิกของกลุ่มมาเป็นผู้เข้าร่วมของนัดหมายได้ โดยต้องจัดการกรณีที่บุคคลเดียวกันถูกเลือกซ้ำจากหลายแหล่งอย่างเหมาะสม

---

## FR-04 Meeting / Appointment Management

ระบบต้องสามารถสร้างนัดหมายหรือการประชุม โดยมีข้อมูลที่จำเป็น เช่น:

- หัวข้อ
- รายละเอียด
- วันและเวลาเริ่มต้น
- วันและเวลาสิ้นสุด หรือระยะเวลา
- ผู้จัดการประชุม
- ผู้เข้าร่วม
- สถานที่หรือลิงก์ประชุมออนไลน์
- สถานะของการประชุม

ระบบควรรองรับการแก้ไข เลื่อน และยกเลิกการประชุม

การประชุมแต่ละครั้งต้องสามารถจัดการเป็นรายการที่แยกจากกันได้

---

## FR-05 Meeting Types

ระบบควรรองรับอย่างน้อยสองลักษณะ:

### One-shot Meeting

การประชุมที่เกิดขึ้นเป็นครั้งเดียวและไม่มีความจำเป็นต้องมีบริบทต่อเนื่องจากการประชุมอื่น

### Project / Continuous Meeting

การประชุมที่เป็นส่วนหนึ่งของงานหรือโครงการระยะยาว ซึ่งอาจมีการประชุมหลายครั้งจนกว่าโครงการหรือกิจกรรมจะเสร็จสิ้น

การประชุมต่อเนื่องไม่จำเป็นต้องเกิดตามช่วงเวลาคงที่ เช่น ทุกวันจันทร์ หรือทุกสัปดาห์

---

## FR-06 Project-based Meeting Management

ระบบต้องสามารถเชื่อมโยงการประชุมหลายครั้งเข้ากับงานหรือโครงการเดียวกันได้

ตัวอย่าง:

Project A

- Meeting 1 — Kickoff
- Meeting 2 — Progress Review
- Meeting 3 — Design Review
- Meeting 4 — Final Review

แต่ละ Meeting ต้องยังคงเป็นนัดหมายที่แยกจากกัน และสามารถมี:

- วันเวลาต่างกัน
- ผู้เข้าร่วมต่างกัน
- Notes ต่างกัน
- เอกสารต่างกัน
- สถานะต่างกัน

---

## FR-07 Reusable Online Meeting Link

ระบบต้องรองรับการบันทึกลิงก์ประชุมออนไลน์ เช่น Microsoft Teams

ผู้ใช้อาจสร้าง Teams Meeting ภายนอกระบบ แล้วนำ URL มาเก็บไว้ในระบบ

ระบบต้องรองรับกรณีที่ลิงก์เดียวถูกนำกลับมาใช้กับการประชุมหลายครั้ง เช่น ห้องประชุมออนไลน์ของโครงการที่ใช้ตลอดช่วงหนึ่งเดือน

ดังนั้น การประชุมแต่ละครั้งไม่จำเป็นต้องมี Online Meeting URL ที่ไม่ซ้ำกัน

ระบบไม่จำเป็นต้องสร้าง Microsoft Teams Meeting ผ่าน Microsoft Graph API ในขอบเขตพื้นฐานของโครงงาน

---

## FR-08 Calendar Invitation (.ics)

ระบบควรสามารถสร้าง Calendar Invitation ในรูปแบบมาตรฐาน `.ics`

ข้อมูลใน Calendar Invitation ควรประกอบด้วยข้อมูลที่จำเป็น เช่น:

- ชื่อการประชุม
- วันและเวลา
- รายละเอียด
- Online Meeting URL หรือสถานที่
- ข้อมูลที่จำเป็นสำหรับ Calendar Application

ไฟล์ควรสามารถนำไปใช้กับ Calendar Application ที่รองรับมาตรฐาน iCalendar เช่น Google Calendar, Microsoft Outlook และ Apple Calendar

ผู้รับอาจต้องยืนยันหรือเพิ่ม Event เข้าปฏิทินด้วยตนเอง ทั้งนี้ขึ้นอยู่กับ Email/Calendar Client ที่ใช้งาน

---

## FR-09 Invitation Delivery

หลังจากสร้างนัดหมาย ระบบควรสามารถส่งข้อมูลการประชุมไปยังผู้เข้าร่วมผ่านอีเมล

อีเมลควรมี:

- ชื่อการประชุม
- วันและเวลา
- รายละเอียดสำคัญ
- ลิงก์ประชุม
- Calendar Invitation หรือข้อมูลที่ช่วยให้เพิ่มลง Calendar ได้
- ข้อมูลเตรียมตัวก่อนประชุม หากมี

การส่งอีเมลอาจดำเนินการผ่าน Third-party Email Service

รายละเอียดการเลือกผู้ให้บริการ Email Service ไม่ใช่สาระหลักของโครงงาน

---

## FR-10 Reminder Management

ระบบต้องรองรับการแจ้งเตือนก่อนการประชุม โดยไม่พึ่งพา Calendar Recurrence เพียงอย่างเดียว

ตัวอย่างการตั้ง Reminder:

- 7 วันก่อนประชุม
- 2 วันก่อนประชุม
- 1 วันก่อนประชุม
- 1 ชั่วโมงก่อนประชุม

การประชุมหนึ่งครั้งสามารถมี Reminder ได้มากกว่าหนึ่งรายการ

ระบบควรสามารถทราบได้ว่า Reminder ใด:

- ยังไม่ถึงเวลาส่ง
- ส่งแล้ว
- ส่งไม่สำเร็จ
- ถูกยกเลิก

ระบบควรป้องกันการส่ง Reminder เดิมซ้ำโดยไม่ตั้งใจ

---

## FR-11 Meeting Notes

ระบบต้องสามารถเก็บ Meeting Notes ของการประชุมแต่ละครั้งได้

Notes อาจประกอบด้วย:

- สรุปการประชุม
- ประเด็นสำคัญ
- สิ่งที่ได้หารือ
- ข้อสรุป
- สิ่งที่ต้องติดตามต่อ

ระบบควรสามารถเรียกดู Notes จากการประชุมก่อนหน้าที่เกี่ยวข้องได้

---

## FR-12 Related Resources

การประชุมสามารถมีข้อมูลประกอบได้หลายรายการ เช่น:

- URL
- เอกสารอ้างอิง
- Presentation
- Shared document
- Repository URL
- เอกสารจากการประชุมครั้งก่อน

ขอบเขตพื้นฐานของระบบไม่จำเป็นต้องเชื่อม Google Drive หรือ Google Docs API

ระบบสามารถจัดเก็บชื่อ รายละเอียด และ URL ของ Resource แทนได้

---

## FR-13 Decisions

ระบบควรสามารถบันทึกสิ่งที่ได้ตัดสินใจจากการประชุม

Decision ควรสามารถย้อนกลับไปตรวจสอบได้ว่าเกิดขึ้นจากการประชุมใด และเกี่ยวข้องกับโครงการใดหากการประชุมนั้นอยู่ภายใต้โครงการ

---

## FR-14 Action Items

ระบบควรสามารถบันทึกงานหรือสิ่งที่ต้องดำเนินการต่อจากการประชุม

Action Item ควรมีข้อมูลที่เหมาะสม เช่น:

- รายละเอียดงาน
- ผู้รับผิดชอบ
- วันที่กำหนด
- สถานะ
- การประชุมต้นทาง

ระบบควรสามารถตรวจสอบได้ว่า Action Item ใดยังไม่เสร็จสิ้นเมื่อกำลังเตรียมการประชุมครั้งถัดไป

---

# 4. AI-assisted Meeting Preparation

## FR-15 AI Pre-meeting Summary

สำหรับการประชุมที่อยู่ภายใต้โครงการหรือมีบริบทต่อเนื่อง ระบบควรสามารถใช้ AI ช่วยสร้าง Pre-meeting Summary

AI สามารถใช้ข้อมูลที่มีอยู่ในระบบ เช่น:

- Meeting Notes ก่อนหน้า
- Decisions ก่อนหน้า
- Action Items
- Action Items ที่ยังไม่เสร็จ
- หัวข้อของการประชุมครั้งใหม่
- Resources ที่เกี่ยวข้อง

เพื่อสร้างข้อมูลสรุปก่อนประชุม

---

## FR-16 Pending Issues Analysis

AI ควรสามารถช่วยระบุประเด็นจากการประชุมก่อนหน้าที่อาจต้องนำกลับมาพิจารณา เช่น:

- เรื่องที่ยังไม่ได้ข้อสรุป
- งานที่ยังไม่เสร็จ
- Decision ที่ยังต้องการข้อมูลเพิ่มเติม
- ประเด็นที่ควรติดตาม

ผลลัพธ์จาก AI ถือเป็นข้อมูลช่วยตัดสินใจ ไม่ใช่ข้อมูลที่ถูกต้องโดยอัตโนมัติ

---

## FR-17 New Agenda Context

เมื่อผู้ใช้ระบุหัวข้อสำหรับการประชุมครั้งใหม่ ระบบอาจให้ AI วิเคราะห์ความสัมพันธ์ระหว่าง:

- หัวข้อใหม่
- Meeting Notes ก่อนหน้า
- Pending Issues
- Action Items
- Decisions

เพื่อสร้างคำแนะนำสำหรับ Agenda หรือ Pre-meeting Brief

---

## FR-18 AI Usage Scope

AI ไม่จำเป็นต้องถูกเรียกใช้กับทุก Meeting

สำหรับ One-shot Meeting ผู้ใช้สามารถสร้างและส่งคำเชิญโดยไม่ต้องใช้ AI

AI ควรถูกใช้เมื่อการประชุมมีบริบทสะสม หรือผู้ใช้ต้องการให้ระบบวิเคราะห์ข้อมูลจากการประชุมก่อนหน้า

---

# 5. Business Rules

## BR-01

บุคคลหนึ่งสามารถเป็นสมาชิกของหลายกลุ่มได้ และกลุ่มหนึ่งสามารถมีสมาชิกหลายคนได้

## BR-02

การลบบุคคลออกจากกลุ่มต้องไม่ทำให้ประวัติการเข้าร่วมประชุมในอดีตสูญหาย

## BR-03

การเปลี่ยนสมาชิกของกลุ่มในภายหลังไม่ควรทำให้ข้อมูลผู้เข้าร่วมของการประชุมในอดีตเปลี่ยนตามโดยอัตโนมัติ

## BR-04

ผู้เข้าร่วมประชุมสามารถมาจากหลายแหล่ง เช่น การเลือกโดยตรง การเลือกผ่านกลุ่ม หรือการเพิ่มอีเมลภายนอก

ระบบต้องจัดการข้อมูลซ้ำอย่างเหมาะสม

## BR-05

การประชุมแต่ละครั้งต้องมีข้อมูลระบุตัวเอง และสามารถแก้ไข เลื่อน หรือยกเลิกโดยไม่กระทบการประชุมครั้งอื่นโดยไม่จำเป็น

## BR-06

Project หนึ่งสามารถมี Meeting ได้หลายครั้ง แต่ Meeting หนึ่งไม่จำเป็นต้องอยู่ภายใต้ Project

## BR-07

การประชุมใน Project เดียวกันไม่จำเป็นต้องมีผู้เข้าร่วมชุดเดียวกัน

## BR-08

การประชุมต่อเนื่องไม่จำเป็นต้องใช้ Calendar Recurrence

แต่ละ Meeting สามารถถูกสร้างเป็น Event แยกกันเพื่อให้สามารถจัดการ Reminder, Notes, Decisions และ Action Items ได้อย่างอิสระ

## BR-09

Online Meeting Link หนึ่งสามารถถูกนำไปใช้กับ Meeting หลายครั้งได้

## BR-10

การแก้ไข Online Meeting Link ต้องไม่ทำให้ข้อมูลทางประวัติศาสตร์สูญหายหรือเกิดความกำกวมโดยไม่ตั้งใจ

## BR-11

Meeting หนึ่งสามารถมี Reminder ได้หลายรายการ

## BR-12

Reminder แต่ละรายการต้องสามารถตรวจสอบสถานะการส่งได้

## BR-13

ระบบต้องสามารถป้องกันการส่ง Reminder เดิมซ้ำโดยไม่ตั้งใจ

## BR-14

หาก Meeting ถูกยกเลิก Reminder ที่ยังไม่ถูกส่งของ Meeting นั้นไม่ควรถูกส่งต่อไป

## BR-15

Meeting หนึ่งสามารถมี Notes, Resources, Decisions และ Action Items ได้หลายรายการตามความเหมาะสม

## BR-16

Action Item ต้องสามารถติดตามสถานะได้อย่างน้อยในระดับที่แยกงานที่เสร็จแล้วออกจากงานที่ยังค้างได้

## BR-17

ข้อมูลการประชุมในอดีตควรยังสามารถเรียกดูได้เพื่อใช้เป็นบริบทของการประชุมครั้งถัดไป

## BR-18

AI-generated Summary หรือ Recommendation ต้องถูกมองว่าเป็นข้อมูลที่ระบบสร้างขึ้นเพื่อช่วยผู้ใช้ และไม่ควรแทนที่ข้อมูลต้นฉบับ

## BR-19

ระบบควรรักษา Meeting Notes และข้อมูลต้นฉบับที่ใช้สร้าง AI Summary เพื่อให้สามารถตรวจสอบย้อนกลับได้

## BR-20

การสร้าง AI Summary ใหม่ไม่ควรทำลายข้อมูล Meeting Notes ต้นฉบับ

# 6. Suggested User Workflow

## Scenario A: One-shot Meeting

1. ผู้ใช้สร้าง Meeting
2. ระบุหัวข้อ วัน และเวลา
3. เลือกผู้เข้าร่วม
4. เพิ่ม Teams URL หากต้องการ
5. ตั้ง Reminder
6. ระบบส่ง Invitation
7. ผู้รับสามารถเพิ่มนัดหมายลง Calendar
8. ระบบส่ง Reminder ตามเวลาที่กำหนด

AI ไม่จำเป็นสำหรับ Workflow นี้

---

## Scenario B: Project Meeting

1. ผู้ใช้เลือก Project
2. ระบบแสดง Meeting History
3. ระบบแสดง Action Items และ Pending Issues
4. ผู้ใช้ระบุหัวข้อสำหรับ Meeting ครั้งใหม่
5. AI วิเคราะห์บริบทเดิมร่วมกับหัวข้อใหม่
6. ระบบสร้าง Pre-meeting Summary
7. ผู้ใช้ตรวจสอบและแก้ไขข้อมูล
8. ผู้ใช้เลือกผู้เข้าร่วม
9. เลือก Online Meeting Link ที่มีอยู่ หรือระบุ Link ใหม่
10. ตั้ง Reminder
11. ส่ง Invitation พร้อม Pre-meeting Summary
12. หลังประชุม ผู้ใช้บันทึก Notes, Decisions และ Action Items
13. ข้อมูลเหล่านี้กลายเป็นบริบทสำหรับ Meeting ครั้งถัดไป

---

## Scenario C: Quick Group Invitation

1. ผู้ใช้สร้าง Meeting
2. เลือกกลุ่ม เช่น “Project A Team”
3. ระบบเตรียมรายชื่อสมาชิก
4. ผู้ใช้สามารถเพิ่มหรือนำบางคนออกสำหรับ Meeting ครั้งนี้
5. ระบบบันทึกผู้เข้าร่วมของ Meeting
6. การแก้ไขสมาชิกของ Group ในอนาคตต้องไม่เปลี่ยนประวัติ Meeting นี้

# 7. Data and Database Expectations

นักศึกษาต้องวิเคราะห์ Requirements และ Business Rules เพื่อออกแบบฐานข้อมูลด้วยตนเอง

การออกแบบควรแสดงให้เห็นความสามารถในการจัดการข้อมูลประเภทต่าง ๆ เช่น:

- บุคคล
- กลุ่ม
- การเป็นสมาชิกของกลุ่ม
- โครงการ
- นัดหมาย/การประชุม
- ผู้เข้าร่วม
- Online Meeting Resources
- Reminder
- Meeting Notes
- Related Resources
- Decisions
- Action Items
- AI-generated Information
- ประวัติการดำเนินการที่จำเป็น

นักศึกษาต้องพิจารณาเองว่า:

- Entity ใดควรแยกจากกัน
- Relationship ใดเป็น One-to-One, One-to-Many หรือ Many-to-Many
- Primary Key และ Foreign Key ควรออกแบบอย่างไร
- Constraint ใดจำเป็น
- ข้อมูลใดควร Unique
- ข้อมูลใดควรเก็บประวัติ
- การลบข้อมูลควรเป็น Hard Delete หรือ Soft Delete ในกรณีใด
- จะป้องกันข้อมูลซ้ำและรักษา Referential Integrity อย่างไร

# 8. Expected Database Queries / Operations

ระบบที่ออกแบบควรสามารถรองรับคำถามหรือการทำงาน เช่น:

1. แสดงสมาชิกทั้งหมดในกลุ่มที่กำหนด
2. แสดงทุกกลุ่มที่บุคคลหนึ่งเป็นสมาชิก
3. แสดงผู้เข้าร่วมของ Meeting
4. แสดง Meeting ที่กำลังจะเกิดขึ้น
5. แสดง Meeting ทั้งหมดของ Project
6. แสดง Meeting History ตามลำดับเวลา
7. แสดง Reminder ที่ถึงเวลาต้องส่ง
8. แสดง Reminder ที่ส่งไม่สำเร็จ
9. แสดง Action Items ที่ยังไม่เสร็จ
10. แสดง Action Items ของบุคคลที่กำหนด
11. แสดง Decisions จาก Meeting ก่อนหน้า
12. แสดง Online Meeting Link ที่ถูกใช้กับหลาย Meeting
13. แสดง Meeting Notes ที่เกี่ยวข้องกับ Project
14. รวบรวมข้อมูลที่จำเป็นสำหรับสร้าง Pre-meeting Summary
15. แสดงผู้เข้าร่วมที่ถูกเชิญผ่าน Group และ/หรือถูกเพิ่มโดยตรง

# 9. Technical Scope

สามารถใช้เทคโนโลยีตามความเหมาะสม เช่น:

- PostgreSQL / Supabase สำหรับฐานข้อมูล
- Supabase Authentication หากต้องการระบบ Login
- Supabase Edge Functions หรือ Backend API สำหรับ Server-side Logic
- Third-party Email API สำหรับส่ง Invitation และ Reminder
- `.ics` สำหรับ Calendar Invitation
- Microsoft Teams URL ที่ผู้ใช้สร้างจากภายนอกระบบ
- Generative AI API สำหรับ Pre-meeting Analysis

เทคโนโลยีที่ระบุเป็นตัวอย่าง ไม่ใช่ข้อบังคับ เว้นแต่ผู้สอนกำหนดเพิ่มเติม

เพื่อให้โครงงานยังคงเน้น Database และไม่ซับซ้อนเกินไป ขอบเขตพื้นฐานไม่บังคับให้ทำ:

- Google Calendar API integration
- Google Docs API integration
- Google Drive permission management
- การพัฒนา Mail Server เอง
- Calendar synchronization แบบเต็มรูปแบบ
- Video conferencing system

- ระบบ Project Management เต็มรูปแบบ

นักศึกษาสามารถพัฒนาความสามารถเหล่านี้เป็น Optional Feature ได้ หากระบบหลักเสร็จสมบูรณ์แล้ว

# 11. Key Design Principle

หัวใจของโครงงานนี้คือ **การออกแบบและจัดการข้อมูลของกระบวนการประชุมที่มีความต่อเนื่อง**

ระบบไม่ควรถูกมองว่าเป็นเพียงระบบ “ส่งอีเมลนัดประชุม”

นักศึกษาควรแสดงให้เห็นว่า Database สามารถช่วยจัดการความสัมพันธ์ระหว่าง:

**People → Groups → Projects → Meetings → Participants → Reminders → Notes → Decisions → Action Items → Next Meeting**

ได้อย่างถูกต้อง มีประสิทธิภาพ และสามารถตรวจสอบย้อนหลังได้

การส่งอีเมล, `.ics`, Microsoft Teams Link และ AI เป็นกลไกที่นำข้อมูลในฐานข้อมูลไปใช้ให้เกิดประโยชน์ในสถานการณ์จริง
